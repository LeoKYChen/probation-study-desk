## 三、如何判定「官方可回查」

每一件新增的關聯裁判，均來自父裁判官網提供的歷審 JSON，而非測試程式自行猜造識別碼：

1. 對既有 7 件父裁判逐一讀取官方頁面、取出歷審 key；只連到 `judgment.judicial.gov.tw/controls/GetJudHistory.ashx`。
2. 比對原先的歷審項目數，7 件均與上輪一致，合計 27 項。
3. 對新的、合法且可供公開回查的關聯識別碼，**重新建構**嚴格的官方 HTTPS `FJUD/data.aspx?ty=JD&id=...` 查詢，不直接信任歷審 JSON 中任何任意網址。
4. 只在官網回應包含符合該**關聯裁判本身**法院、案號、年度、字別、號數，並且官方結構化裁判日期與 JID 日期一致、存在實質正文區塊時，才判 `passed`。
5. 有空連結、非官方網域、非允許法院或案號、日期對不上、無法開啟或無正文者，不會被列為通過；本輪報告沒有把「HTTP 200」當作充分證據。
6. **沒有再取得 MCP 全文、沒有核對這 7 件新關聯裁判的 MCP 擷取文字，亦沒有追查每個關聯裁判的下一層歷審鏈**。這是「官網可回查性」，不是「17 件全文已驗收」。

## 四、隱私、安全及規模限制

- 第一批：最多 7 次父裁判 GET、7 次官方歷審清單 GET、14 次關聯裁判 GET；實際只查 6 件新關聯文書。補測：再讀取一件父裁判與歷審清單，**只取一件原先未核對的關聯裁判**。
- 不查專門少年家事法院、不以少年／家事案號查文書；不登入會員 API、不取用有效帳密或 Token。
- 不跟隨非官方轉址，不做重試或防護繞過。
- JSON 報告只保留原本已知父裁判的分組代碼、項目數、比對結果布林值及原因分類；**不保存、輸出、提交新關聯裁判的 JID、案名、原文、當事人、歷審說明文字、HTML 或 PDF**。
- 所有實作及測試限於 `experiments/v27-mcp-poc/`、獨立 `.github/workflows/`。沒有修改 `main`、v2.5、`development/v2.7/`、`services/v2.7-judgment/`、Cloudflare 或部署任何公開裁判查詢端點。

## 六、下一輪建議

原訂 10 件父裁判與 7 件新增關聯裁判的**來源可回查性**已經取得相當明確的證據。下一階段應優先補強 **不同裁判日期、長篇判決與非典型 HTML／PDF** 的來源與擷取穩定性，而不是重做已完成案件。
