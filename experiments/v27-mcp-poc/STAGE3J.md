# v2.7 × MCP｜第 3 階段第十輪（Stage 3j）：10 件裁判歷審清單比對

分支：`experiment/v27-mcp-stage3j`，以第九輪 `experiment/v27-mcp-stage3i` 的 **10 件來源／日期／文字擷取忠實性已核對**樣本為基礎。

## 為什麼不能直接宣告「十件歷審完整」？

研究版本 `lawchat-oss/mcp-taiwan-legal-db`（固定 SHA：`ef677ad63c3206fc211a083fad8b1d9ef5015222`）的 `judicial_doc.py`：
- 從官網裁判書頁取得 `GetJudHistory.ashx?jid=...` 的歷審識別碼，讀取官方 JSON `list`；
- 將每筆歷審項目轉為 `desc`、`jid`、`url`、`pending_supreme_court`；
- **歷審資料使用獨立的 24 小時快取**，與裁判正文長期快取分離；
- 官方清單缺漏、取得失敗、不含上一審或上級審資料，不等於案件沒有歷審。
- MCP 原始碼的 `history_note` 亦明文警示：「清單最後一筆之後沒有更高審級，不等於已經確定（可能仍在上訴期間內，或上級審裁判尚未上網）。」

## 本輪 3 級驗收項目

| 層級 | 稽核內容 | 可通過的結論 |
| --- | --- | --- |
| L1 官網清單存在性 | 個別裁判官網 `#jud` 可讀、官方頁包含 history key，且獨立取得 `GetJudHistory.ashx` 的 JSON 清單 | 官網歷審清單於取用當時可取得 |
| L2 MCP 清單忠實性 | 獨立 JSON 各筆的歷審 JID、網址、清單文字與 pending 標記與 MCP 逐欄比較；不含全文 | 在該次查核，MCP 所提供的歷審清單忠實反映官網資料 |
| L3 歷審完整／裁判確定 | 每一可能相關的原審、上級審裁判可獨立回查，確認法院／案號／裁判日期、異動狀況及確定資訊 | **此輪不宣告 L3 通過**；即使 L1/L2 10／10 成立，也不等於所有可能上訴均已查得 |

## 負面結果判定

- 官網歷審 key 不存在、HTTP 403／timeout、官方 JSON 格式錯誤：`review`，不當作沒有歷審。
- 官網清單為空：可能確實沒有列出任何歷審，但**不代表裁判已確定**。僅在 MCP 亦回空清單且有警語時可作「空清單一致性」有限判定。
- MCP 仍有 24 小時快取、清單項目數或文字／URL／狀態與官方不一致：`review`，不得將舊清單誤認為官方現況。
- 非司法院網域、可疑歷審連結、非官方 JID：拒絕比對且標明來源問題；不得跟隨第三方轉址。
- 歷審中有尚未公開的裁判、只有案件繫屬註記或上級審尚無裁判：不得猜測裁判結果，不補寫不存在的全文。

## 隱私／來源限制

本次僅限 10 件已確認的公開法院文書，各最多一次官方裁判頁面、一次官方歷審 JSON，以及一次固定版本 MCP 呼叫。**不抓歷審關聯裁判全文**，不追出一整串裁判，也不查少年事件未公開裁判。

報告僅保留已知公開 JID、是否有歷審、清單數量、URL／項目／pending／文字是否對應、明確的失敗類別；**不儲存或輸出任何裁判正文、當事人、歷審說明原文、案情或其他關聯 JID**。MCP 暫存資料位於 GitHub Actions 臨時路徑，不加入公開儲存庫。
